## 1. Objetivo

Detectar automáticamente regresiones de lint, formato y pruebas del backend antes
de integrar una pull request en `develop`. El resultado debe reproducir los
comandos obligatorios del proyecto y mostrar fallos reales sin modificar pruebas,
ocultar errores ni convertir avisos preexistentes en éxitos.

## 2. Reglas y documentos involucrados

No modifica reglas RN-xx. Aplica `docs/conventions.md`, que exige CI en verde y
al menos una aprobación humana, `docs/testing-database.md`, el engine Node del
backend y el protocolo de `docs/errores-inducidos.md`. La excepción académica
solo podrá aplicarse a un defecto concreto, documentado y autorizado; no cubre
fallos generales del workflow.

## 3. Alcance

**Incluye:** un workflow versionado para pull requests hacia `develop`, Node 24,
PostgreSQL 16 aislado, instalación reproducible desde el lockfile y ejecución de
lint, formato y suite completa del backend. Debe cancelar o serializar ejecuciones
obsoletas de la misma PR y exponer cada resultado de forma comprensible.

**No incluye:** despliegue, publicación de imágenes, secretos de producción,
pruebas con `.env`, integración automática, aprobación automática, cambios de
dependencias, corrección incidental de módulos ajenos, frontend o ramas `main`.

## 4. Flujo principal propuesto

1. GitHub recibe o actualiza una pull request dirigida a `develop`.
2. El runner obtiene el commit exacto de la PR y prepara Node 24.
3. PostgreSQL 16 arranca con credenciales ficticias exclusivas del job.
4. `npm ci` instala exactamente el lockfile desde `backend/`.
5. Se ejecutan `npm run lint`, `npm run format:check` y `npm test` sin omitir suites.
6. Cualquier comando con salida distinta de cero deja el check fallido y conserva
   el diagnóstico; el workflow no integra ni aprueba la PR.

## 5. Datos y configuración

El workflow solo usa variables de prueba definidas en el job. `DATABASE_URL`
debe apuntar al servicio PostgreSQL del runner con nombre de base terminado en
`_test`, conforme al guard del proyecto. No se leen `.env`, credenciales reales,
tokens de aplicación ni datos persistentes. No requiere migraciones nuevas.

## 6. Superficie afectada

No añade endpoints. El archivo previsto es
`.github/workflows/backend-quality.yml`; su nombre final puede ajustarse durante
la revisión sin cambiar el contrato. Los scripts ejecutados deben ser los ya
versionados en `backend/package.json`.

## 7. Criterios de aceptación

- [ ] Una PR hacia `develop` inicia el workflow sobre su commit actual.
- [ ] Node 24 y PostgreSQL 16 se muestran explícitamente en la ejecución.
- [ ] Lint, formato y `npm test` se ejecutan sin `continue-on-error`, exclusiones
      nuevas, cambios de expectativas ni ampliaciones de timeout.
- [ ] Un fallo intencional de comprobación en una rama de prueba produce un check
      rojo y un diagnóstico localizable; la rama no se integra como parte de CI-01.
- [ ] Una ejecución satisfactoria no imprime `DATABASE_URL`, contraseñas, cookies
      ni tokens.
- [ ] Dos actualizaciones rápidas de la misma PR no consumen runners manteniendo
      resultados obsoletos como si fueran actuales.
- [ ] La documentación explica cómo reproducir localmente los mismos comandos.

## 8. Casos borde y errores

- PostgreSQL no saludable: fallar el job; no sustituirlo por mocks.
- Lockfile desactualizado: `npm ci` falla y se reporta sin ejecutar `npm install`.
- Timeout o prueba intermitente: conservar el fallo y reproducirlo antes de
  decidir una corrección; CI no reintenta automáticamente la suite.
- Fork o permisos limitados: no usar secretos que impidan comprobar una PR.
- Fallos inducidos autorizados: documentar la excepción concreta según el
  protocolo; no usar `continue-on-error` para toda la suite.
